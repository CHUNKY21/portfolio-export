AI Pattern Library

A design system for AI states.

A defined set of reusable AI-interaction components — confidence, sourcing, in-progress response, correction, human handoff — documented and governed the same way as any other design-system component, so product teams stop reinventing AI trust patterns from scratch.

“We built confidence three different ways across three teams, and none of them talk to each other.” Illustrative, constructed for this case study — not a verbatim interview quote.

What's the AI Pattern Library?

A minimal, documented set of AI-interaction components — Confidence/Certainty Indicator, Citation/Source Card, Streaming-Response State, Correction/Feedback Control, and Human-Handoff Banner — governed and adopted the same way Michael has run design-system rollouts at Wells Fargo and Credit Suisse, applied here to a category of interface state that traditional design systems were never built to cover.

Standard design systems have a button, a table, a modal. They don't have an agreed answer for "here's a source citation," "here's how confident this answer is," "the response is still streaming in," or "tell the AI it got this wrong." This case study is a synthesis of what it looks like to close that gap using the same governance discipline already proven on non-AI systems.

  • Every team invents its own confidence visualization, with no shared visual or verbal language
  • Citation/sourcing shown inconsistently across teams, undermining trust in the product family
  • No shared "still generating" affordance — users can't tell if the system finished or stalled

Discovery methods: organizational audit of AI features already shipped across product teams; interviews with the designers/PMs who built them and the design-system governance stakeholders who'd need to support adoption; review of publicly published external AI-design guidance as a reference point.

Problem statement: standard design systems don't have components for AI-specific states — there's no established pattern for showing a source, showing confidence, showing an in-progress response, or telling the AI it got something wrong.

Pain points from interviews

  1. Every team invents its own confidence visualization, with no shared visual or verbal language for "sure" vs. "not sure"
  2. Citation/sourcing shown inconsistently — some teams show it by default, others bury it, some don't show it at all
  3. No shared "still generating" affordance — users can't tell if the system finished or stalled
  4. No consistent way for a user to tell the system it got something wrong, with no visible consequence where a control exists at all
  5. No consistent way to hand off to a human when the AI shouldn't finish the task alone

Design & Process — 8-stage AI-Enhanced UX Process

1. Discovery & Research

Same as always: an organizational audit and stakeholder interviews, the same starting point used for every real design-system engagement.

New: mapped what's genuinely reusable across any AI feature vs. what's necessarily product-specific — a boundary question that didn't exist for buttons and modals.

2. Problem Definition

Same as always: synthesized the audit into a named pain-point list.

New: separated "the pattern doesn't exist yet" (a design system can solve this) from "users don't trust AI output in this domain" (only the interaction design of each component solves that).

3. Competitive / Pattern Analysis

New: the "competitor" is internal — every other team's ad hoc solution — benchmarked against publicly published external AI-design guidance as a reference point, not a traditional feature-parity scan.

4. Design Thinking & Ideation

New: ideation defined each component's behavior independent of any one product's implementation, with the adoption/governance question treated as part of ideation, not an afterthought.

5. Design Sprints & Iteration

Same cadence as prior non-AI design-system work: iterative rounds with pilot teams.

New: iterating on a component whose underlying data is non-deterministic (a confidence score, a streaming response) rather than a fixed screen.

6. Usability Testing

New: tested trust and comprehension at the component level, and adoption at the governance level — do teams actually implement the pattern as documented.

7. Delivered Solution

New: the "component" delivered is a state/behavior as much as a screen — v1 ships 5 documented components with an explicit boundary between what the pattern owns and what stays product-specific.

8. Outcomes

See Results below — targets, not measured results.

What we learned The confidence indicator's first draft used red/yellow/green. Pilot review found red collided with the org's existing error-color language, reading as "something's broken" instead of "the system isn't sure." Redesigned around a neutral intensity scale plus a plain-text qualifier — an accessibility fix that also fixed the semantic collision.
